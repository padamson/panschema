# ADR-010: Migrations as Versioned Artifacts Beside a Declarative Source

## Status
Proposed

## Context

Every output panschema writes today is *derived*: run `generate` twice and
the second run overwrites the first with the same bytes. `verify` leans on
exactly that — regenerate, compare, fail on drift. The model is the single
source of truth and the artifacts are disposable.

A database schema does not work that way. The tables carry data, and moving
existing tables from one shape to another is a sequence of `ALTER`
statements that has to be applied in order, once, and recorded. So a
consumer whose LinkML schema drives generated Rust types and generated
Postgres DDL currently has a gap: `generate --format postgres` emits a full
`CREATE TABLE` script, which is useful exactly once, on an empty database.
After that they are hand-writing DDL, which is the thing the schema was
supposed to spare them.

The question this ADR settles is what kind of thing a migration *is* in a
project built around a declarative source, and what that implies for how
panschema may write one.

### What the runner requires

The target is a checksumming versioned runner — `refinery` and the family
it belongs to. Four of its behaviors are not preferences to design around;
they are constraints:

1. **Applied migrations are immutable to the byte.** `Migration::unapplied`
   hashes the migration's name, version, and *raw* SQL text with SipHasher13
   and no normalization at all. The hash is stored on apply and compared on
   every subsequent run. A trailing newline, a CRLF, or a regenerated
   version banner changes it, and the default response to a mismatch is to
   abort the whole run before applying anything.
2. **Tolerating a mismatch is worse than failing on one.** The runner's
   "ignore divergence" setting downgrades the abort to a log line and then
   *skips* the migration, leaving the database on the old schema while the
   model claims otherwise. That is silent, permanent drift. (Its CLI ships
   with the opposite default from its library, which makes this easy to hit
   by accident.)
3. **Appending is safe; inserting is not.** A migration whose version is at
   or below the highest already applied is rejected. A separate `U` prefix
   exists for out-of-order insertion, and the discovery pattern is
   `^([U|V])(\d+(?:\.\d+)?)__(\w+)` — so the descriptive half of a filename
   is word characters only, and a file that does not match is skipped in
   silence rather than reported.
4. **Everything runs in a transaction, with no opt-out.** A request for a
   per-migration escape hatch was closed upstream as not-planned. So
   `CREATE INDEX CONCURRENTLY` and its relatives cannot appear in generated
   output.

Point 1 is the one that bites hardest, because panschema's existing habit
runs straight into it: the Postgres writer opens every script with
`-- @generated by panschema v<version>`. Emitting that line into a migration
would change every consumer's stored checksum on every panschema upgrade,
and abort their next deploy.

## Decisions

**1. The schema stays the source of truth; migrations are a versioned
artifact beside it, not a second source.**

The delta is always derived from schemas — never by introspecting a live
database. That keeps the whole feature database-free, which is the property
worth protecting: it works in CI, on a laptop, and against a schema whose
database does not exist yet. Migrations are the *record* of deltas already
emitted, not an independent description of the model.

**2. Emitted migrations are append-only and immutable.**

panschema never rewrites a file it has emitted, never re-emits the full
schema as a replacement, and never renumbers. This is a direct consequence
of constraints 1 and 3 above, and it is the rule that makes the hybrid safe:
because migrations are append-only, "the schema is the source of truth" and
"the migrations are authoritative history" do not conflict.

Squashing is the obvious violation and is not offered. A compaction command
that rewrote history into a single migration would invalidate every stored
checksum. If it is ever justified — a fresh start before a first deploy —
it goes behind an explicit flag, never a default.

**3. Generated output is deterministic, which means no tool version and no
timestamps.**

`migrate` renders the DDL through a version-free path
(`postgres_writer::render_migration_body`) rather than the writer's normal
`render`. Everything in a migration is derived from the schema alone. The
same schema produces the same bytes on any machine and any panschema build,
so an upgrade does not abort a deploy.

This is a deliberate divergence between two outputs of the same writer:
`generate --format postgres` keeps its `@generated` banner, because that
file *is* regenerated and the banner tells a reader not to edit it. A
migration is not regenerated, so the banner would be both wrong and
harmful.

**4. `generate` does not write migrations; `migrate` does.**

A manifest may declare `migrations = "db/migrations/"` in a
`[generate.<name>]` block, alongside the other outputs. But `generate`
skips that key. Every other output there is safe to rewrite on every run;
this one is not, and folding an append-only artifact into the
regenerate-everything command would either make `generate` refuse on its
second run or make it quietly append migrations as a side effect of
building docs. Neither is acceptable, so the destructive-adjacent operation
gets its own command and its own invocation.

**5. panschema generates migration files and never applies them.**

No apply, no rollback, no database connection, in any slice. Applying is the
runner's job. Keeping the boundary means there is no destructive command
here to confuse with the generator, and `--help` says so plainly.

**6. A generated migration is a draft to review.**

Every tool in this space takes this position, and stating it is better than
implying the output is trustworthy unreviewed. Structural DDL is what a
schema delta can express; data migrations — backfills, value
transformations — are not derivable from it and are out of scope.

## Consequences

- The Postgres writer now has two rendering entry points, and the difference
  between them is load-bearing rather than cosmetic. A future change that
  adds anything non-deterministic to the shared body breaks consumers'
  deploys, not just their diffs, so the determinism test guards the body
  directly.
- `verify`'s regenerate-and-compare model does not extend to migrations, and
  should not be made to. Drift between the schema and the migration history
  is a question for `diff`, which reports it in schema terms.
- Adopting an existing database — one whose tables were created by some
  other tool — has no answer here. Prior art calls this a baseline
  migration, and it stays an open question rather than something guessed at.
- Because the runner skips unparseable filenames silently, the filename
  shape is a contract with an external crate that panschema does not depend
  on. It is pinned by a test carrying the runner's own discovery pattern, so
  a change on either side surfaces as a failure rather than as migrations
  that mysteriously never run.
